Windows向け **完全一致ファイルの重複調査** と **PNG/JPG完全無劣化の圧縮候補生成** を行う開発中のC# / WPFアプリ。

### 使い捨てWindows環境での本物のごみ箱E2E診断（本番ロック継続）

Windows CIは、標準の人工Core/WPFテストとは**別プロセス**で、GitHub-hosted Windowsランナーにだけ生成する64KiBの重複3件を使った追加診断を行います。専用TEMP＋sentinelを検証し、`検出 → 保留移動2件 → 元の場所へ1件復元 → 残る1件を個別確認 → 実Windows Shellでごみ箱要求 → $I/$R・NTFS ID・SHA独立照合` を試します。環境変数 `CHAPPY_TEST_REAL_RECYCLE_BIN=I_ACCEPT_SYNTHETIC_RECYCLE` と `CHAPPY_TEST_CI_SYNTHETIC_RECYCLE=EXPLICIT_EPHEMERAL_RUNNER` の同時指定が必須で、**通常の本番EXEには経路がコンパイルされません**。処理は他のファイルを一切受け付けない生成TEMP限定です。

CIの診断結果 `diagnostics/duplicate-real-shell-e2e.json` は **`VERIFIED_SYNTHETIC_RECYCLE_PAIR`**（Windowsごみ箱内に同一NTFS ID・内容の独立証拠あり）と **`INCONCLUSIVE_MANUAL_REVIEW` / `INCONCLUSIVE_TIMEOUT_MANUAL_REVIEW`**（非対話環境・拒否・証拠欠落・処理停止）を厳密に分けます。UIダイアログ等で止まった場合は独立プロセスを25秒で強制終了し、自動再試行や完全削除への切替はしません。CIジョブ自体が成功しても、診断結果が `INCONCLUSIVE` であれば**実ごみ箱E2Eの合格を意味しません**。生成ファイルが実ごみ箱に残り得る点も通常ランナーの使い捨てデータだけに限定しています。

この検証は**人のマウス・キーボード操作受入（G5-04）や独立レビュー・本番解禁（G5-06）の代替ではありません**。一般ファイルの重複整理・削除の有効化には、対話型Windows実機での受入と書込経路の独立監査、明示承認が必要です。

### Windowsごみ箱の独立証拠照合（人工データ限定）

追加の `Core/RecycleBinEvidence.cs` は、Windowsのごみ箱で作られる `$I`（元パス・元サイズ・削除時刻）と `$R`（実ファイル）を**両方とも読み取り専用で確認**し、元NTFSファイルID・リンク数・全データSHA-256まで照合します。1件でも不一致、複数候補、未知の形式、読み取り拒否、元パスの再占有があれば成功とは認めません。既存のWindowsごみ箱の内容を変更する仕組みではありません。

`RecycleViaShellSynthetic` に明示的に許可した実Shellテストを行った場合に限り、現在のWindowsアカウントのSID配下にあるごみ箱を独立確認し、一致した人工ファイルだけ**テスト用証拠**を記録します。通常のWindows CIではごみ箱を変更せず、人工的な `$I/$R` の組を使って、正常・破損・ハッシュ違い・ファイルID違い・複数候補・時刻不一致を検証します。ごみ箱を空にされると証拠も失われ得ます。

**この合格は本番の削除許可ではありません。** 製品の重複整理は引き続き読み取り専用。実ごみ箱を用いた対話的な人工ファイルE2E、WPFからの安全な本番実行経路、実機受入・独立安全レビュー・明示承認は未完了です。

### 生成NTFS限定：実WPF確認画面から保留・元パス復元・永続確認・模擬ごみ箱の連結試験

Windows Core smoke の **`CHAPPY_TESTING` ターゲット**は、製品本体の `DuplicateCleanupReviewWindow.cs` と `DuplicateCleanupHistoryWindow.cs` を**同じソースから別アセンブリへリンク**し、生成TEMP+sentinelで検証した3件のランダム重複ファイル（64KiB）だけで、画面のボタン経由の `最終照合 → 実NTFS保留移動2件と最上位一覧TXT → 1件を元パスへID固定復元 → 選択1件を永続確認 → 生成フォルダの模擬ごみ箱へ移動 → 履歴画面で状態確認` を1つの記録で通します。NTFS ID・全バイト・keeper不変を再検証します。**実Windowsごみ箱を使う別の隔離CIはPR #99で既に合格したため、このWPF試験では再実行しません**。

生成用の操作ボタンと `ArmGeneratedOnlyForTests` は `#if CHAPPY_TESTING` で囲み、**出荷するWinExeにはコンパイルされません**。通常版の確認画面で使えるのは個別確認のメタデータ保存・再読込と読み取り専用の最終照合までです。CIでは製品WPFアセンブリから生成用コントロール/アームAPIが存在しないことも検証します。本番の実ファイル保留移動・ごみ箱移動・元パス復元は引き続きロックを維持し、人のWindows操作受入と独立安全レビュー・明示承認は未完了です。

### 重複候補ごとの「確認内容の保存・復元」（メタデータ限定）

重複グループの「整理先・削除候補を確認」を開くと、**「最終照合（読み取り専用）」→「照合済みの確認を保存」**で、チェックした候補だけをWindowsユーザーの `%LOCALAPPDATA%/ChappyStorageCompressor/DuplicateReview/` に保存できます。**元ファイル・最上位フォルダ・整理先・ごみ箱への書き込みは発生しません。** アプリ再起動後も、同じグループを再スキャンして「保存した確認を復元」を押せば、元ファイルID・属性・権限・SHA-256・全バイトと整理予定の再照合が合格した場合に限ってチェックが表示されます。保存済みチェックが勝手に選択・実行されることはありません。

保存内容は現時点のスキャン情報とグループ・元パス・整理予定を識別するフィンガープリントに紐づきます。**確認を取り消して保存**すれば選択0件の状態も保存され、壊れた保存データや変更された候補は復元しません。保存は最新の全候補の最終照合に通らなければ拒否し、記録ファイルの書込失敗を明示します。アプリ内の保存データは**チェックリストのみ**であり、ファイルの削除同意・移動許可・本番実行の承認ではありません。ごみ箱ボタンは引き続き無効です。アプリ設定領域に元ファイルのパス情報が残る点に注意してください。

独立したCIは人工NTFSで記録の保存/再読込/取消/破損拒否/移動後の無効化、および本物のWPFボタンを通る保存/復元と削除ボタン無効を検証します。人がWindowsでマウス・キーボードを操作するG5-04の受入試験や独立レビューG5-06は未完了です。

### 重複整理の保留記録とごみ箱の安全確認（本番ロック継続）

「履歴・復元」タブの **「重複整理の保留記録を確認」** では、検索フォルダ内の `.chappy-cleanup-evidence` を**読み取り専用**で一覧表示できます。元のパス・保留先・残したファイル・途中停止/元パスへの復帰の記録を確認できます。ただし記録の存在・ファイル名の一致はNTFS ID/全バイト/権限が一致する証明ではありません。**この画面からファイルを復元・削除・ごみ箱移動することはできません**。読めない/不正/未知の記録は「要手動確認」です。

人工NTFS限定の `DuplicateCleanupWorkflow.RecycleViaShellSynthetic` には Windows の `Microsoft.VisualBasic.FileIO.FileSystem.DeleteFile` を `RecycleOption.SendToRecycleBin` / `UICancelOption.ThrowException` / 確認画面ありで呼び出す実シェル経路を用意。ただし **`#if CHAPPY_TESTING` 限定**かつ生成TEMP+独自sentinel確認に加え、操作を本当に試すには `CHAPPY_TEST_REAL_RECYCLE_BIN=I_ACCEPT_SYNTHETIC_RECYCLE` の明示環境変数、対話型STA、1MiB以下が必要です。通常のWindows CIは本物のごみ箱を動かさず、拒否・未確認・途中状態を模擬transportで検証します。**Shellから戻って元パスが消えていても、ごみ箱へ安全に入った証明ができないため「要手動確認」のままにし、完了レシートは書きません。** 失敗や取消後も完全削除への自動フォールバック、再実行、元の場所への自動上書きは一切行いません。

この段階は新方式の本番完成ではありません。必要なのは本物のごみ箱上のファイル同定/復元テスト、WPF→耐中断Coreの製品実行経路、実機操作、独立レビューと明示承認です。

### 重複整理の最終再照合（通常のWPF画面・読み取り専用）

重複グループの「整理先・削除候補を確認」から開く画面には、ファイルごとの仮チェックに加え **「最終照合（読み取り専用）」** ボタンがあります。検索時のリストに対し、残す1件・候補全件のNTFS ID/リンク数/サイズ/日時/属性/ACL/ハッシュ/全バイト、および最上位 `同名ファイル` フォルダの競合と `同名ファイル一覧.txt` の連番予定を再確認します。照合はバックグラウンドで実施し、画面を閉じればキャンセルします。候補が1000件を超える場合はこの画面で照合を実行せず分割を促します。

ファイルが変更された場合や整理先が占有された場合は**安全停止**して再スキャンを求めます。チェックの変更後は照合結果を無効化します。**照合に合格してもごみ箱・移動・削除ボタンは無効のまま**です。結果は現在時点の読み取り専用の事前確認であり、永続的な削除承認でも直前TOCTOU保護の代替でもありません。実行可能なファイル変更処理はまだ本番に接続していません。

### 重複の整理先と削除前確認（安全ロック中）

「重複整理」で完全一致グループを開き、残す1件を選んで「整理先・削除候補を確認」を押すと、**元パスと整理予定のフォルダ構造・最上位メモ**を確認できます。既存の `CollisionCollectionPlan` に従い、最上位フォルダの `同名ファイル/元の相対ディレクトリ/ファイル名 (1).拡張子` と `同名ファイル一覧.txt` の予定名を生成します。既存の同名フォルダ・メモがあれば入れ子・連番にして上書きを回避します。メモはコピーできます。

**これは表示とコピーだけ**です。まだファイルの退避・移動、フォルダやメモの作成、ごみ箱への移動、完全削除は行いません。確認チェックは画面上だけの状態であり削除許可ではありません。削除機能を本番利用可能にするには、実行直前の元ID・SHA・全バイト・変更/リンク検査、容量・アクセス権・中断復旧・ごみ箱拒否/失敗処理、記録の永続化、Windows実機受入と明示承認が必要です。単に同一NTFS内で重複を整理用フォルダへ移しても、容量は回復しません。またごみ箱に残っている間も空き容量が増えない場合があります。

### exFAT・ドライブ全体の重複検索（読み取り専用）

- 「重複整理」の検索対象に `E:\\` など**ドライブ直下を入力/選択**できます。ローカルNTFS・exFATを対象とし、exFATのサブフォルダも自動的に「検索専用」へ切り替えます。NTFSの一般フォルダは従来の厳格NTFS検査で、明示的に「検索だけ」を選ぶこともできます。
- 検索専用は、サイズ一致候補を再確認→SHA-256→全バイト比較。内容が完全一致するファイルを一覧表示し、重複の余分な**論理容量の見込み**を表示。削除/ごみ箱/ハードリンク/Undo/整理計画の対象にはなりません。NTFSファイルID、所有者/ACL、ADSの保全証拠は持ちません。
- ドライブ全体を選んでも、Windows管理フォルダ、`System Volume Information`、`$Recycle.Bin`、ジャンクション/リパースポイント、オフライン/システム領域、既存の作業ストアはスキップします。読み取れないファイル・アクセス拒否も除外/エラー件数として表示します。**検索完了はドライブの全領域を網羅した保証ではありません。**
- 外付けドライブは検索中に抜かず、ドライブ全体ではファイル数に応じて時間がかかるので「停止」を利用してください。NTFSの厳格な統合・復元経路にexFATを通すことはありません。FAT32/ネットワーク共有は現在の検索対象外です。
- Windows CIでは生成NTFSデータを使って検索専用経路のWPFボタン・完全一致・読み取り専用属性・除外・停止・不変性を検証します。**実exFAT媒体での手動受入は未実施**です。G5-04/06の正式進捗には算入しません。

## メイン画面の操作（3タブUI）

- **重複整理（最初のタブ）**：フォルダを選んで「重複ファイルを検索」。初期設定では拡張子に関係なく通常ファイルを調べ、既存の安全ルールに従って特殊・危険なファイルを除外します。重複グループの「›」またはダブルクリックで全ファイルのパスを表示します。画像はプレビューでき、右クリックから画像を開く・場所を開く・パスをコピーができます。画像以外は保存場所を開くかパスをコピーします。「残す予定」の指定は**確認用**であり、実際の削除・ごみ箱移動はまだできません。
- **画像圧縮**：PNG/JPG無劣化候補の一括生成と容量レポート。既存の診断機能は「高度な画像操作・診断」に格納。
- **履歴・復元**：復旧ウィザードと履歴の読み取り専用確認。重複整理の統合計画などは「詳細設定・追加の確認」に格納。

削減見込みは未適用の理論値であり、実際の回復容量ではありません。本番の重複削除・ハードリンク統合・Undo・画像原本置換は**未解禁**。初めて触る場合は、人工データまたは複製したテストデータだけを選んでください。

- 3種類の2560×1600人工JPEG×通常版／SIMD版の計6プロセスを実行。独立した出力とアプリ本体の `JpegLosslessPreviewEngine.CreatePreview` の候補をバイト・SHA256・全画素・メタデータで照合。
- 元データは人工生成のみ。原本のSHA-256・更新日時を保護し、実画像・原本置換・ハードリンク統合は本番無効。容量の実回復は0B。
- 値は**生存中に観測できた子プロセス単独のOSピーク常駐メモリ**であり、終了直前の取りこぼしもあり得るため、Chappyアプリ全体の最大使用量や一般的なSIMD優位性の保証ではない。

[試験内容と制限](docs/R217_NATIVE_CHILD_PEAK_MEMORY.md) / [Issue #14](https://github.com/mibesamiti-png/Chappy-Storage-Compressor/issues/14)

## R2.17（第11段階）：最優先の一括検証（1回のPRで3テーマ）

- **1,072件の人工メディア風ファイル**でサイズ分布別のスキャンと完全一致の正解比較を2回ずつ実施。
- **本当に開けるJPEG 6枚・PNG 6枚**を使って本番候補エンジンの生成・独立した全画素照合・双方の作業再開をまとめて検証。
- 大きな人工JPEG 2枚では、アプリ本体と**本体が直接起動したjpegtran子プロセス**のOS常駐メモリを同時に観測。テスト限定のPID通知は製品ビルドには入らない。
- 初回・再実行の速度差はキャッシュ等を制御していない参考値であり、性能向上を保証しない。原本置換・統合・Undoは本番無効、実空き容量回復は0B。

## R2.17（第12段階）：一括候補の進捗・再開UIを改善

- PNGとJPGに固定で50%ずつ割り当てていた進捗表示を、**事前調査のファイル件数に応じた比率**へ変更。処理対象数が偏っていても、読みやすい見込み進捗を表示。
- 連続した通知を**約125msごとに制限**し、WPFの不要な描画イベントを削減。エラー・容量不足・要確認は間引かず通知する。人工通知30,005件の負荷試験を追加（実アプリ高速化の保証ではない）。
- 直前に使用した候補保存先・jpegtranフォルダは**アプリ起動中だけ**選択ダイアログへ提案。毎回ファイル/保存先の明示選択、作業記録の読取専用安全検査と実行確認が必要。
- 実際のWPF Scan/Stopルートを使うUIテストで、作業中のPNG/JPG操作ボタン無効化・中断後の復帰・統合ボタンの安全ロックを確認。
- **原本置換・重複統合は本番無効、実空き容量回復0B。**

## 開発の安全ゲート

1. Windows CIでビルド・合成ファイルの安全テストをすべて通す。
2. ファイルサイズ・バイト内容だけでなくファイルID、ACL、ADS、ハードリンク状態、同時変更の危険性を検証する。
3. 元の写真・動画を削除・上書きする機能は本番検証完了まで**無効**とする。
4. 容量回復は実測の空き容量として報告し、圧縮候補の削減見込みと区別する。

公開リポジトリに個人の写真・動画、ユーザー固有パス、実行ログ、認証情報、バックアップを追加しないでください。旧 `Chappy_Storage_Compressor_R2_6_REDOWNLOAD.zip` は照合用アーカイブで、これからの正本はGit管理されたC#ソースです。
