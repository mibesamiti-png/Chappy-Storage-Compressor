# Chappy Storage Compressor

Windows向け **完全一致ファイルの重複調査** と **PNG/JPG完全無劣化の圧縮候補生成** を行う開発中のC# / WPFアプリ。

> ⚠️ **開発中です。大切な写真・動画の原本には使用しないでください。** 通常版のハードリンク統合・原本置換は安全のため無効です。GitHub Actionsの合格は製品の安全性保証ではありません。

## R2.13：個人用JPG・PNG・MP4の重複容量レポート

開発の優先順位を見直し、**普段のWindowsで使う画像・動画を安全に容量削減すること**へ重点を戻しました。別ユーザーの所有権や複雑なACL継承への対応は後回しにし、特殊属性やADSのあるファイルは安全に除外します。

- 読み取り専用の重複スキャン後、**「JPG / PNG / MP4別の重複容量レポート・CSV」**ボタンから種類別の削減見込を確認。
- 以前のスキャン結果をそのまま信じず、SHA-256・ファイルID・全バイトの一致を**再検証**。変更されたグループは見込み量から外します。
- MP4は**バイト完全一致の重複検出のみ**。再エンコードや画質変更は行いません。
- CSVはユーザーが保存を選んだときだけ出力し、原本フォルダ内への保存・既存ファイルの上書き・表計算式注入を防ぎます。
- **削減見込は論理値で、実際の回復容量は0B**。通常アプリの統合・原本置換・統合解除はまだ無効です。

[仕様と安全範囲](docs/R213_PERSONAL_MEDIA_FOCUS.md) / [PR #9](https://github.com/mibesamiti-png/Chappy-Storage-Compressor/pull/9)

- 特殊属性ファイルの件数は事前見積の対象外として記録。最終的な採否は従来の各形式エンジンが個別に検証。

## R2.15：JPG・PNG圧縮候補とMP4重複の二重計上を防ぐ容量分析

既存の**「PNG/JPG統合容量レポート／CSV」**を拡張。先に同じフォルダを重複スキャンしておけば、JPG・PNG候補の削減見込とMP4を含む完全一致重複の見込を**形式別に補正**して表示します。

- JPG・PNG・MP4別に「重複」「候補」「重複して数えた分」「補正後」の見込を表示。
- 重複スキャン後に内容が変わったファイル、追加ハードリンクができたファイルは再照合で除外。
- 大量データの再照合進捗と中断に対応。
- CSVで形式別補正表と従来の候補詳細表を選んで保存。原本・候補内への出力や同名上書きは拒否。
- MP4の再圧縮は一切せず、ファイルのバイト完全一致のみ対象。**実際に回復した容量は0B**のまま。

## R2.16：大量のJPG・PNG・MP4スキャンを2段階に高速化

読み取り専用の完全一致スキャンを改善。最初はファイルサイズ・日時・属性だけを軽く調べ、**同じサイズのファイルが複数ある場合に限り**NTFSのファイルID・所有者/ACL・代替データストリーム、SHA-256、全バイト比較まで実行します。

- 他に同じサイズのファイルがない場合は、内容読み込み・SHA-256を省略。
- 同じサイズの候補はこれまでどおり厳密に検証し、ADS・共有ハードリンク・特殊属性は除外。
- 画面に「一次調査件数・厳密検査件数・ハッシュ計算件数」を表示。
- 合成JPG・PNG・MP4を使用して検査回数・経過時間・管理メモリ割り当てを測定。実行時間の改善率はWindows環境で変わるため、一定値を保証しません。
- **原本の削除・置換・統合は無効**。回復した実際の空き容量は0Bのまま。

[2段階スキャンの仕組みと測定条件](docs/R216_TWO_STAGE_SCANNER_BENCHMARK.md)

## R2.17（第1段階）：同一サイズが多い大量ファイルの合成負荷試験

- 約110MiBの生成データで、ファイルサイズが全部違う場合と同じサイズが大量にある場合をそれぞれ2回測定するWindowsテストを追加。
- 同一サイズの76ファイルに対し、厳密NTFS検査76件・SHA-256計算73件・安全な重複3グループを検証。ADSと既存ハードリンクは除外する。
- Windowsプロセスの読み取り転送量・時間・管理メモリ割当・プロセスメモリを記録。ただし、物理ディスク読み取り量や厳密なコールドキャッシュ速度ではない。
- ハッシュ計算の進捗を最大およそ20回の頻度で更新するよう改善。巨大な1ファイルの途中の進捗表示は次工程。
- テストは生成バイナリのみであり、実在のJPEG/PNG形式を使う候補生成性能検証はまだ。原本置換・ハードリンク統合は無効、実際の容量回復は0B。

## R2.17（第2段階）：デコード可能なPNG・JPEGの一括処理プロファイル

- 人工生成した**本当に開けるPNG 12枚・JPEG 12枚**を用いて、候補作成の負荷を計測するテストを追加。
- PNGは既存の一括無劣化候補エンジンを直接実行。候補の画素完全一致を独立のWindows画像デコーダーでも検証し、中断・再開記録を再利用。
- JPEGは有効な画像のマーカー検査・全画素復号・一括処理計画を計測。**外部のjpegtran.exeは実行していないため、JPEG候補生成速度は未測定**。
- CRC、原本のSHA-256、進捗回数、所要時間を検証し、匿名の合成計測データをCI成果物として保存。
- 生成PNGは再圧縮しやすい構造を含むため、削減効果を実際の写真に当てはめない。原本の置換や重複統合は引き続き無効で、実際の容量回復は0B。

[測定手順と残る課題](docs/R217_VALID_IMAGE_BATCH_PROFILE.md) / [未完了のIssue #14](https://github.com/mibesamiti-png/Chappy-Storage-Compressor/issues/14)

## 開発の安全ゲート

1. Windows CIでビルド・合成ファイルの安全テストをすべて通す。
2. ファイルサイズ・バイト内容だけでなくファイルID、ACL、ADS、ハードリンク状態、同時変更の危険性を検証する。
3. 元の写真・動画を削除・上書きする機能は本番検証完了まで**無効**とする。
4. 容量回復は実測の空き容量として報告し、圧縮候補の削減見込みと区別する。

公開リポジトリに個人の写真・動画、ユーザー固有パス、実行ログ、認証情報、バックアップを追加しないでください。旧 `Chappy_Storage_Compressor_R2_6_REDOWNLOAD.zip` は照合用アーカイブで、これからの正本はGit管理されたC#ソースです。
