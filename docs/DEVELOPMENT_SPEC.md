# Chappy Storage Compressor — 仕様・段階・注意点

## 目的

空き容量が少ないHDD/SSDの親フォルダを選択し、JPG/PNG/MP4の画質・映像・内容を変えることなく容量を回復。元のフォルダ構造とファイル名を残す。

## 原則

- **完全一致の判定**はファイルサイズ → SHA-256 → 全バイト比較。
- **完全無劣化**はビット同一（R1の重複統合）と、将来的な画素同一・音声/映像ストリーム同一（無劣化最適化）を区別して実装。
- R1では**バイト列を一切変更しない**。JPEG/PNG/MP4の再圧縮は実装しない。
- 自動スキャンは読み取り専用、統合はユーザーの選択と最終確認が必要。
- 同じボリュームのNTFSハードリンクを使用。統合先は選んだ親フォルダの `.ChappyDedupeStore`。
- ファイルサイズ・タイムスタンプ・ACL・属性・ファイルIDを取得して、同一性と統合リスクを判定。
- 厳格モードでは属性・セキュリティ記述子・作成日時・更新日時が一致しないものは除外。日時差の許容は追加の明示確認。
- シンボリックリンク、ディレクトリジャンクション、ドライブ直下、特殊属性ファイル、すでにハードリンクがあるファイル等はR1で除外。

## 統合手順

1. 親フォルダにある実ファイルをスキャンし、統合対象を表示。
2. 選択されたグループについて、代表ファイルの同一性とSHA-256を再確認。
3. 統合先に代表ファイルへのハードリンクを作る（新たなファイル内容のコピーなし）。
4. 個々の重複ファイルについてスキャン時のメタ情報、SHA-256、全バイト一致を再確認。
5. `%LOCALAPPDATA%` 内に復旧用JSONジャーナルをディスクへフラッシュしてから、原本ファイルを同じフォルダ内の退避名に移動。
6. 元のパスに統合先へのハードリンクを作成し、同一NTFSファイルIDを検証。
7. 退避した独立コピーのSHA-256と全バイト比較を再実行し、問題がなければその退避コピーだけ削除。
8. ジャーナルを削除。途中エラー時は可能な限り元のパスへ退避ファイルを戻し、できない場合は復旧記録を保持。
9. 操作後は再スキャンが必要（元ファイルのファイルIDが変わるため）。

## 異常終了時

- 元パスがない＋退避がある → ユーザー確認後に元パスへ退避を移動。
- 元パスがある＋退避がある → **どちらも消さず**人間による確認が必要。
- 元パスがある＋退避がない → 完了済みの可能性。記録を消すがファイル内容の保証はしない。
- 両方がない → **どちらも消さず**人間による確認。

## 安全テスト

`RUN_TESTS.bat` はランダムなテストフォルダ内でのみ、作成したバイナリデータを `.jpg` として扱い、比較、統合、リンクID、バイト同一性、再スキャンを検査。画像のデコードテストではない。失敗時は本番データに適用しない。

## 技術の限界

元ファイルへのハードリンクを作る操作はファイルの完全同一を保証するものではなく、**同じデータを共有する**操作。編集時の独立性を失う。復旧のためのジャーナルは停電やファイルシステム障害に対する完全なトランザクションを提供しない。保存先は別ボリュームにできない。スキャン結果から処理開始までの同時更新には一定の競合リスクがあるため、実行時にアプリや同期サービスのアクセスがないことが望ましい。

**リスク登録**:
- RISK-001: ハードリンクの破壊的共有（編集時に別パスの内容も変更される）
- RISK-002: OS停電・競合プロセスで完全なトランザクション保証なし
- RISK-003: NTFS ADS/ACLの取り落とし（現版ではADSは拒否、ACLは照合）
