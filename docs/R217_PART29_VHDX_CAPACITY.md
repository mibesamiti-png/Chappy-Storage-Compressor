# R2.17 Part 29 — isolated VHDX allocation, Undo cost, and real Core low-space refusal

## Prior evidence and this new boundary

R2.8 already measured real allocated bytes and noisy host-volume free-space deltas from a generated synthetic NTFS directory. Parts 23–28 established generated-only Core hardlink merge, saved per-alias/group history, and controlled worker-kill Undo. **None of this freed user-media capacity**; the production merge, original replacement and Undo remain disabled.

Part29 adds two *complementary* CI safety gates, rather than assuming free-space readings are atomic reservations:

1. **Real Core low-space refusal:** `CapacityGuard` exposes an internal `CHAPPY_TESTING`-only observation delegate, absent entirely from production builds. The Core smoke test runs the actual `DedupeEngine.Run` on three generated identical MP4-like files and independently injects below-reserve target and recovery-journal capacity at the first preflight, after a temporary master link is created but before the transaction journal, and before a later alias after one successfully committed alias. It must preserve every original byte and NTFS identity; remove an unneeded temporary master when no alias commits; keep the already committed alias and the not-yet-merged alias intact; never leave an unresolved recovery transaction. Target reserve = 4 MiB, separate journal reserve = 2 MiB. These are conservative observed thresholds, *not* space reservations.
2. **Actual mounted isolated VHDX:** `bootstrap/Part29IsolatedVhdxProbe.ps1` runs only on ephemeral Windows GitHub Actions, accepts **no user-specified paths**, and creates a unique GUID+sentinel directory immediately beneath `RUNNER_TEMP`. Using DiskPart, it creates a **new expandable 512-MiB VHDX**, attaches and formats only the selected newly generated virtual disk as NTFS, and assigns a *new empty generated mount directory*. There is no command to select, clean, reformat or assign a letter to an existing host disk. The script verifies the mounted volume GUID differs from the host, filesystem and label match, and uses native `GetDiskFreeSpaceExW`, `GetCompressedFileSizeW`, and `GetFileInformationByHandle` to measure true volume-local free space, allocated bytes, hardlink count and NTFS file IDs. Two generated 8-MiB independent files are consolidated via hardlink; the virtual volume must gain capacity, then reallocate space when the alias is independently restored via `File.Replace`. Finally, only the generated 512-MiB volume is filled below the 4-MiB target reserve; original synthetic bytes and independent IDs must remain unchanged. The exact generated VHDX is detached before deleting its GUID folder; unsafe/uncertain detach refuses cleanup. No real user photos/videos are read or modified.

Strict CI evidence: `diagnostics/r217-part29-core-low-space.json` and `diagnostics/r217-part29-isolated-vhdx.json`. The VHDX test **must report a separate mounted NTFS volume and real positive free-space deltas to pass**; CI cannot silently substitute the earlier host-volume measurement when VHDX mounting is unavailable. The existing R2.8–2.12 checks and Parts 1–28 stay enabled.

## Limitations and remaining release gates

Windows hosted runners may reject VHDX attach/partition operations depending on privileges and virtualization support. **If the test cannot safely create the isolated volume, Part29 is not proven and the CI gate must fail**, without weakening requirements or claiming experimental results. No physical device power-off, cache flushing guarantee, arbitrary ACL/SACL/ADS/EFS or a race-proof reservation primitive is demonstrated. The VHDX measurement uses generated native hardlinks and `File.Replace`, not the normal WPF app or arbitrary end-user media; the separate Core low-space test uses real Core routines with deterministic injected observations. A real drive-space reading can change immediately after preflight, and conservative safety locks must remain.

Production hardlink consolidation, independent Undo and original PNG/JPG replacement remain **disabled**. Real-user recovered space is **0 B**, while the historical 69.4% source estimate is neither current progress nor shipping readiness. Require successful full PR-head Windows CI before merge, and independently confirm postmerge main CI.
