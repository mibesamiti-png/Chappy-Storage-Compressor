# R2.17 — Prioritized grouped performance and safety matrix (part 11)

## Goal and batch boundary

Rather than one experimental fixture per PR, this change groups three high-priority **real application code paths** into one source-pinned Windows CI integration run:

1. **Large read-only media-like duplicate scanner:** 1,024 independent nested files with distinct sizes and 48 same-size files including exactly four duplicate pairs. Inspect counts, hashes and group identities using independent framework SHA-256 and byte oracle. Run each distribution twice to record timing without assuming the first read is cold.
2. **Genuine valid JPEG/PNG batch candidate creation:** six WPF-encoded JPEGs and six syntactically correct, intentionally uncompressed PNGs. Run the app's `JpegBatchPreviewEngine.Run` with official source-pinned jpegtran and `PngBatchPreviewEngine.Run` to generate true candidate outputs. Independently verify decoded pixels and protected JPEG metadata, then resume both batch journals and assert no duplicate candidates. Record generation, first-run and resume phase timings.
3. **Real app + exactly launched native JPEG child combined memory observation:** two synthetic 2560×1600 JPEG sources through `JpegLosslessPreviewEngine.CreatePreview`. A **test-only compile-time `CHAPPY_TESTING` callback** reports only the exact JPEG child PID started by that engine; the test polls Windows parent working set alongside that child's OS-maintained `PeakWorkingSet64`, recording the largest simultaneous observed parent-plus-native value. The diagnostic callback is *not compiled into production* and makes no actual media changes.

A separate fail-closed Windows CI step enforces both machine-readable JSON reports from one shared release branch. Existing 516 C# safety checks, real WPF build/UI routed scan tests, pinned libjpeg-turbo source tools, synthetic NTFS fault/recovery checks and win-x64 EXE publish must remain green.

## Reproducibility and what the numbers mean

- Deterministic generated bytes and WPF-encoded valid images; synthetic input only. The large scan's media extensions are **media-like random bytes**, *not* valid decodable JPEG, PNG or MP4. Valid codec images are a separate 6+6 dataset.
- Scanner test covers two independent distributions, two nominal passes each, 1,072 total generated files. No real cold-cache flush, actual physical disk bytes or hardware-tier comparison is claimed. Exact output groups are independently SHA-256 and byte-verified.
- Image phase timings (creation, candidate runs, resume and memory observation) are separate; they include WPF, NTFS, journal and validation overhead and are not codec-only microbenchmarks. No claimed deterministic speedup, optimization result or stable throughput.
- Combined parent-plus-child observation records **parent current working set + native child's previously reached OS peak as sampled during the same interval**. This is an explicitly *conservative sum of different memory-time semantics*, not exactly synchronized true combined instantaneous resident memory, not private committed bytes and not the guaranteed full lifetime maximum. Short child exits or final peaks may escape the sampler; no observations is a test failure.
- On low memory, large media or different Windows host/build, performance can differ greatly. Current test fixtures do not prove worst-case 48MP behavior.
- Safety invariants: generated sources unchanged (hash and timestamp), output in separate disposable directories, no original replacements, no hardlink deduplication, no real media touched. **Physical end-user disk capacity recovered 0 B**.

The 1,024 items are small; do not compare their durations directly to a small count of large files as an algorithmic speedup. Real media volume benchmarking and physical HDD/SSD reads remain pending.

Six generated valid JPEG and six deliberately *uncompressed* valid PNG files were processed by their **real application batch engines**. All six JPEGs and all six PNGs produced smaller accepted candidates; 6/6 in each format independently passed all decoded WPF pixels and protected JPEG marker equality, with source hash/time unchanged.

They do not demonstrate an encoder speed increase or normal photo compression ratios.

### Actual application process + exact native child observed together

Two additional **2,560×1,600 generated JPEGs** were run through `JpegLosslessPreviewEngine.CreatePreview` with a TEST-BUILD-ONLY child-PID observer (absent from the shipped production app). For each, the independent test successfully observed **two** polling instants when both the parent process and its exact child were alive. The largest **observed parent-current working set + child OS-maintained peak working-set counter** was:

| Generated JPEG case | Real engine time | Parent+native observed counter sum | Child observed peak |
| --- | ---: | ---: | ---: |
| Structured image | **56.69 ms** | **140,062,720 B** (~133.6 MiB) | **15,728,640 B** |
| Alternate structured image | **47.65 ms** | **125,513,728 B** (~119.7 MiB) | **15,728,640 B** |

**Critical limits:** These parent+child numbers do not represent synchronized instantaneously resident memory (the native child field is a historical peak as of sampling); just **two live joint observations** per case cannot rule out a higher short-lived peak. They also include *all allocations from the test host process* and are **not** a representative Chappy production WPF instance's peak. No RAM decrease or speedup can be inferred from these numbers. Missing child observations explicitly fail the gate rather than passing by guessing.
